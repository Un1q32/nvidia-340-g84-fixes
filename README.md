# NVIDIA 340.108 on a MacBook Pro 4,1 (GeForce 8600M GT), modern glibc + glvnd

This repository documents and reproduces the fixes that make the **last NVIDIA
driver branch for the G84M (8600M GT), 340.108**, work on a *modern* Gentoo
userspace:

* glibc 2.43
* libglvnd 1.7.0
* Xorg 1.20.14
* kernel 5.4.302
* 64-bit and 32-bit

It fixes two independent problems:

1. **Xorg crashed during GLX init** with
   `malloc(): unaligned tcache chunk detected`.
   Root cause: NVIDIA's `libnvidia-tls.so.340.108` calls
   `arch_prctl(ARCH_SET_FS, <heap address>)`, moving the thread's TLS base
   away from glibc. glibc 2.43 then reads `tcache` from the wrong memory.
2. **GLX/3D did not work** even after the crash was fixed.
   Root cause: 340.108 predates libglvnd vendor support, so there is no
   `libGLX_nvidia.so.0`. The libglvnd dispatchers (`libGLX.so.0`,
   `libOpenGL.so.0`) only had Mesa's backend, which cannot drive the NVIDIA
   server.

The result:

```
OpenGL renderer string: GeForce 8600M GT/PCIe/SSE2
OpenGL version string: 3.3.0 NVIDIA 340.108
direct rendering: Yes
```

## The two fixes

### 1. libnvidia-tls: use the official `tls/` variant

The 340.108 `.run` installer ships **two** `libnvidia-tls` builds:

| file | size | syscalls | behaviour |
|---|---|---|---|
| `libnvidia-tls.so.340.108` | 12696 | 2 | does `ARCH_GET_FS` / `ARCH_SET_FS` |
| `tls/libnvidia-tls.so.340.108` | 13008 | 0 | normal glibc TLS |

The `tls/` variant is the correct one for a glvnd/glibc system. Install it over
the default one (64- and 32-bit):

```sh
nvidia/install-tls-variant.sh
```

This is a **binary replacement**, not a source patch; the replacement file is
the official NVIDIA build from the same installer. See
`nvidia/README-libnvidia-tls.md` and `nvidia/checksums.txt` for identification.

### 2. libglvnd shims

340.108 has no `libGLX_nvidia.so.0`. We point the glvnd dispatchers at NVIDIA's
monolithic `libGL.so.340.108`:

```
/usr/lib64/libGL.so.1     -> libGL.so.340.108
/usr/lib64/libGLX.so.0    -> libGL.so.340.108
/usr/lib64/libOpenGL.so.0 -> libGL.so.340.108
```
and the same for `/usr/lib32`.

`ldconfig` rewrites `libGLX.so.0`/`libOpenGL.so.0` based on the glvnd SONAMEs,
so the fixup runs `ldconfig` **first**, then creates the symlinks. That ordering
is what makes the setup survive package updates.

## Update safety

`system/nvidia-340-fixups.sh` re-asserts all of the above. It is run:

* at boot by `system/nvidia-340-fixups.init` (OpenRC, `before display-manager`),
* after relevant package merges by `system/portage-bashrc`
  (`/etc/portage/bashrc`, `EBUILD_PHASE=postinst`), covering
  `media-libs/libglvnd`, `media-libs/mesa`, `x11-base/xorg-server`,
  `x11-drivers/nvidia-drivers`, `x11-apps/mesa-progs`, `media-libs/freeglut`.

The hook uses `addwrite` so it can re-create the symlinks inside the Portage
sandbox. The boot service handles anything the hook misses (e.g. a driver
reinstall done outside Portage).

This was tested by rebuilding `media-libs/libglvnd`: the package overwrites all
three symlinks, and the postinst hook restores them immediately; `glxgears`
keeps working without a reboot.

## Portage packages

No ebuild patches or pkg-config overrides are required. Standard packages work
through the shims:

```sh
emerge x11-apps/mesa-progs media-libs/freeglut
glxinfo -B
glxgears
```

The old workarounds (pkg-config overrides forcing `-lGL`, a freeglut CMake
patch) were removed; they are no longer needed.

## Xorg

Use **Xorg 1.20.x**. 340.108 supports server ABI 24; Xorg 1.21+ (ABI 25) will
break. `system/package.mask/xorg-server-121` blocks that. The server GLX module
must be NVIDIA's:

```
/usr/lib64/xorg/modules/extensions/libglx.so -> libglx.so.340.108
```

Build Xorg with GLX enabled (the default ebuild configuration). Do not build it
with `--disable-glx`.

## Kernel module

The kernel module source is unmodified NVIDIA 340.108. On GCC 16 the manual
build needs relaxed error flags:

```sh
kernel/build-nvidia-340-module.sh
```

## From scratch

The driver itself is proprietary and is **not** in this repository. The full
flow on an OpenRC Gentoo system:

```sh
# 1. download, verify and extract the official 340.108 .run
sudo NVIDIA_WORK=/root nvidia/fetch-driver.sh
# -> /root/NVIDIA-Linux-x86_64-340.108

# 2. stop the desktop and install the userspace (no kernel module)
sudo rc-service display-manager stop
sudo NVIDIA_SRC=/root/NVIDIA-Linux-x86_64-340.108 nvidia/install-userspace.sh

# 3. build the unmodified kernel module (GCC 16 flags)
sudo NVIDIA_SRC=/root/NVIDIA-Linux-x86_64-340.108 \
     kernel/build-nvidia-340-module.sh

# 4. TLS fix + glvnd shims + boot service + Portage hook + Xorg mask
sudo NVIDIA_SRC=/root/NVIDIA-Linux-x86_64-340.108 ./install.sh

# 5. Xorg 1.20.x (ebuild + patches included)
#    see xorg/overlay/README.md
sudo emerge --oneshot =x11-base/xorg-server-1.20.14
```

Then reboot and verify:

```sh
tools/verify.sh
DISPLAY=:0 XAUTHORITY=/home/uniq/.Xauthority glxinfo -B
```

## 32-bit binaries (Steam / games)

The 32-bit userspace has the same two problems as 64-bit. They are applied by:

```sh
sudo NVIDIA_SRC=/root/NVIDIA-Linux-x86_64-340.108 nvidia/patch-32bit.sh
```

That replaces the 32-bit `libnvidia-tls` with the official `32/tls/` build and
points `/usr/lib32/libGL.so.1`, `libGLX.so.0` and `libOpenGL.so.0` at NVIDIA's
32-bit `libGL`. The boot service and Portage hook maintain the same 32-bit
links, so package updates do not undo them. Verify with:

```sh
tools/verify-32bit.sh
```

The NVIDIA installer does **not** provide the 32-bit X11 runtime. Steam and
32-bit games need it; install the `abi_x86_32` X11 packages (see
`nvidia/README-32bit.md`). On the tested system `steam-launcher` also required
`sys-libs/libudev-compat` to be unmasked (`~amd64`).

## Caveats

* Pointing `libGLX.so.0`/`libOpenGL.so.0` at NVIDIA's libGL effectively
  **disables libglvnd's Mesa path**. This is intentional: the G84 has no usable
  Mesa hardware driver, and 340 has no glvnd vendor. Mesa software rendering via
  glvnd will not work while these shims are active.
* Do not build large packages with `-j6` on a 2-core/2.9 GB machine; it wedges
  the box. Use `MAKEOPTS="-j2"` and `nice` for Xorg/glibc builds.
* `intel_iommu=off` is required on this MacBook for the driver's EVO path.
* The `.run` installer may reinstall the FS-hack `libnvidia-tls` and the glvnd
  files. Run `nvidia/install-tls-variant.sh` and
  `system/nvidia-340-fixups.sh` afterwards (or reboot; the boot service does the
  latter).
